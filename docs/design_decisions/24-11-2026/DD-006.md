# DD-006: Result Type for Operation Outcomes

**Date:** 2026-11-24  
**Status:** Accepted  
**Area:** Architecture / Error Handling

### Context

Engine operations need a consistent way to communicate whether they succeeded or failed.

Returning only a boolean would communicate the outcome but would not provide information about the cause of failure.

Returning only an error value would require special values to represent successful operations.

A common Result representation should provide both the operation outcome and its associated error information.

### Decision

Operations that require explicit failure reporting use a Result type.

A Result contains two fields:

- A boolean indicating whether the operation succeeded.
- A packed error value describing the failure.

The boolean is the authoritative indicator of operation success.

A successful Result must satisfy the following conditions:

- The success boolean is `true`.
- The error value is `ARC_ERROR_NONE`, whose numeric value is zero.

A failed Result must satisfy the following conditions:

- The success boolean is `false`.
- The error value is nonzero and represents the cause of failure.

The severity of an error does not determine the success state of a Result.

A failed Result may contain an error classified with any valid non-`NONE` severity, including `WARNING`.

### Consequences

- Operations have a consistent way to communicate success and failure.
- Callers can check operation success without interpreting error severity.
- Failure information is available through the packed error value.
- The Result representation remains independent of individual subsystem error definitions.
- Successful operations have a canonical Result state.

### Alternatives Considered

**Returning only a boolean**

Rejected because it does not provide information about the cause of failure.

**Using only the error value to represent operation outcomes**

Rejected because it would make operation success dependent on interpreting special error values.

# DD-002: Separation of Path and FileSystem

**Date:** 2026-11-24  
**Status:** Accepted  
**Area:** Architecture / Platform Abstraction Layer / File System

## Context

The filesystem abstraction is intended to support multiple filesystem implementations, such as physical disk filesystems, in-memory filesystems, archive-based filesystems, and virtual filesystems.

A path and a filesystem implementation represent different responsibilities. A path describes a location in a structured form, while a filesystem implementation provides the operations that act on that location.

Tying path representation directly to a particular filesystem implementation would make paths less reusable and would complicate support for multiple filesystem implementations.

## Decision

The filesystem abstraction separates these responsibilities into two distinct concepts:

1. **Path**
2. **FileSystem**

A `Path` is an independent object representing a filesystem path in a structured form. It is not tied to a particular filesystem implementation.

A `FileSystem` represents a filesystem implementation through an interface based on function pointers. The interface provides operations for working with files and directories.

Filesystem operations accept `Path` objects rather than arbitrary path strings. Individual filesystem implementations are responsible for interpreting those paths and performing the requested operations.

The exact set of path and filesystem operations will be defined separately as the filesystem design is developed.

## Consequences

- Path representation is separated from filesystem implementation.
- Filesystem operations receive a structured path object.
- Multiple filesystem implementations can use the same Path abstraction.
- New filesystem implementations can be introduced without embedding their behavior into Path.
- The abstraction can support physical, virtual, memory-based, and archive-based filesystems.

## Alternatives Considered

### Using arbitrary strings for filesystem operations

Rejected because strings provide no dedicated path abstraction and would leave path handling conventions to individual callers or filesystem implementations.

### Embedding filesystem-specific behavior in Path

Rejected because it would couple Path to particular filesystem implementations and reduce its reusability.

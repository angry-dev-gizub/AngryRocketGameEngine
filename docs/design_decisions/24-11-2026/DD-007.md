# DD-007: Separation of Result Handling and Resource Cleanup

**Date:** 2026-11-24  
**Status:** Accepted  
**Area:** Architecture / Error Handling / Memory Management

### Context

The Result model could optionally contain residual resource ownership when an operation fails to release a resource during cleanup.

This approach was used in the Arc project to represent allocations that could not be released after an operation failed.

However, ordinary memory deallocation through the standard C allocation interface does not provide a recoverable failure result. Invalid deallocation attempts, such as double frees or freeing pointers that do not belong to an allocator, are programming errors and may result in undefined behavior.

Other engine resources, such as operating-system handles and graphics resources, may have release operations that can report failures. These operations have different contracts from ordinary memory deallocation.

Combining all these cases into a generic residual ownership mechanism would introduce additional complexity into the Result representation.

### Decision

The generic Result type must not contain a Residue or transfer ownership of residual resources.

The Result type is responsible only for representing operation success or failure and the associated packed error value.

Ordinary memory deallocation follows the contract of its allocator and is not represented as a fallible Result operation.

Resource destruction operations that can legitimately report failures may return a Result containing the corresponding error.

Cleanup and ownership handling remain the responsibility of the subsystem that owns the resource.

If a future subsystem requires a mechanism for transferring ownership of resources after incomplete cleanup, that mechanism must be designed separately according to the resource's specific requirements.

### Consequences

- The generic Result representation remains small and straightforward.
- Ordinary memory deallocation does not introduce unnecessary failure states.
- Programming errors in memory management are not treated as recoverable runtime failures.
- Fallible resource destruction can still report errors.
- Resource ownership and cleanup remain explicit responsibilities of the relevant subsystem.
- A general residual ownership mechanism is not introduced without a concrete requirement.

### Alternatives Considered

**Including residual ownership in every Result**

Rejected because most operations do not need to transfer residual resources, and ordinary memory deallocation does not provide a meaningful recoverable failure state.

**Treating every resource destruction operation as infallible**

Rejected because some external resource-management APIs can legitimately report failures.

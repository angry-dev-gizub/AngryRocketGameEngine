# DD-001: Integration of the Platform Abstraction Layer into Core

**Date:** 26-11-2026  
**Status:** Accepted  
**Area:** Architecture

## Context

Originally, Angry Rocket was designed with two independent libraries:

- Platform Abstraction Layer (PAL)
- Core

PAL was intended to provide operating-system abstractions, while Core provided general-purpose functionality such as memory management, containers, algorithms, and data structures.

However, maintaining these as independent libraries introduces unnecessary complexity and redundancy.

Both libraries would require their own fundamental mechanisms, including error handling, allocator interfaces, and other shared infrastructure.

The primary benefit of keeping them separate would be allowing PAL to be reused independently of Angry Rocket Core. However, its functionality is primarily intended to support the engine, and independent reuse does not justify the additional architectural complexity.

## Decision

The Platform Abstraction Layer will be integrated into Angry Rocket Core as an internal subsystem rather than maintained as an independent library.

Platform-specific functionality will be organized under a dedicated Platform component within Core.

This component will provide functionality such as:

- Operating system detection.
- Architecture detection.
- SIMD capability detection.
- Threading.
- Filesystem operations.
- Networking.
- Other operating-system abstractions.
- Interfaces to relevant external platform libraries.

PAL functionality will use Core's existing infrastructure, including its allocator abstraction, error representation, and Result API.

The Platform component will remain internally separated from other Core components through clearly defined interfaces.

## Consequences

- PAL and Core no longer require separate allocator abstractions.
- PAL and Core share one error representation and Result API.
- Redundant infrastructure and error translation are avoided.
- Platform functionality remains organized and separated within Core.
- Core becomes easier to maintain as a single library.
- PAL can no longer be independently built or used as a separate library.
- Platform-specific implementation details must remain isolated behind appropriate interfaces.

## Alternatives Considered

### Maintaining PAL as an independent library

Rejected because the benefits of independent reuse do not justify the additional complexity and duplicated infrastructure.

### Allowing PAL to depend on Core while remaining a separate library

Rejected because this would introduce an unnecessary library dependency and weaken the original reason for separating the two components.

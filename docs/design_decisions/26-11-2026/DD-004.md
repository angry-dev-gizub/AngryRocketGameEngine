# DD-004: Error Source Identification

**Date:** 26-11-2026  
**Status:** Accepted  
**Area:** Error System

## Context

Angry Rocket interacts with multiple operating-system interfaces and external libraries.

These interfaces frequently define their own error codes. Different providers may use identical numerical values to represent completely different errors.

For example, a numerical error code from Windows does not necessarily have the same meaning as the same numerical code from POSIX or GLFW.

The error representation must preserve the origin of these codes.

## Decision

The error representation includes an 8-bit Source field.

This field identifies the error-code namespace or provider associated with the error.

Possible sources include:

- Angry Rocket.
- Windows.
- POSIX.
- GLFW.
- Other external libraries.

The Source field is not limited to operating systems.

For engine-defined errors, an Angry Rocket-owned source identifier will be used.

For native or external-library errors, the corresponding provider will be identified.

The Source field will have a reserved value representing the absence of an external or provider-specific source, where appropriate.

## Consequences

- Native error codes can be preserved without losing their origin.
- Errors from external libraries can coexist with engine-defined errors.
- Error-code interpretation becomes unambiguous when the source namespace is considered.
- Additional providers can be introduced without changing the overall error representation.
- The engine must maintain a consistent set of source identifiers.

## Alternatives Considered

### Using only a Platform field

Rejected because error sources are not necessarily operating systems. External libraries such as GLFW also define their own error codes.

### Converting every external error into an Angry Rocket error code

Rejected as the universal approach because doing so can lose the original error identifier and additional provider-specific information.
